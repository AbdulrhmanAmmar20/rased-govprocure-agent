# وثيقة متطلبات النظام — «راصد» (GovProcure Agent)

> نظام وكيل الذكاء الاصطناعي للامتثال وتدقيق المشتريات الحكومية
> الإصدار: 1.0 — حالة الوثيقة: معتمدة كمرجع للتنفيذ

---

## 1. نظرة عامة ونطاق المشروع

### 1.1 الهدف

أتمتة مراجعة وتدقيق عروض الموردين وعقود الشراء المباشر والمنافسات بناءً على
**نظام المنافسات والمشتريات الحكومية ولائحته التنفيذية**، مع عزل البيانات وضمان
سيادتها عبر سحابة سيادية محلية، ومنع تسريب البيانات الشخصية والتجارية الحساسة.

### 1.2 المشكلة المستهدفة

1. استغراق فترات طويلة في فحص وتدقيق العروض والمطابقة النظامية.
2. خطر الوقوع في مخالفات رقابية:
   - تجاوز سقوف الشراء المباشر.
   - إهمال نسب المحتوى المحلي.
   - غياب الاعتماد المالي المسبق.
3. تعذر استخدام النماذج الذكية العامة (مثل OpenAI العامة) لمخالفتها نظام حماية
   البيانات الشخصية (PDPL) ولوائح الهيئة الوطنية للأمن السيبراني (NCA).

## 2. أدوار المستخدمين ومصفوفة الصلاحيات (RBAC)

| الدور | الوصف | الصلاحيات البرمجية |
|---|---|---|
| **أخصائي مشتريات**<br/>`Procurement Specialist` | موظف فني ومعدّ للمعاملة | رفع العروض، استعلام الوكيل عن مطابقة اللائحة، إنشاء مسودات مذكرات الفحص.<br/>**لا يملك** صلاحية اعتماد الميزانية أو إصدار أوامر الصرف. |
| **مدقق نظامي**<br/>`Compliance Auditor` | مراجع ومراقب قانوني | استعراض سجلات التدقيق (Audit Logs)، التحقق من تفسيرات الوكيل للوائح ومطابقتها للمواد النظامية. |
| **صاحب صلاحية / مدير إدارة**<br/>`Approver / Director` | المسؤول المالي والإداري | اعتماد مذكرات الترسية النهائية، الموافقة على المعاملات المعلقة بنظام Human-in-the-Loop، وإصدار أوامر الشراء المباشر. |
| **مدير النظام**<br/>`System Admin` | مهندس أمن وبرمجيات | إدارة إعدادات البنية التحتية، تحديث قواعد بيانات اللوائح المتجهة (Vector DB)، ومراقبة مؤشرات الأداء والأمان. |

## 3. المتطلبات الوظيفية (Functional Requirements)

### FR-1: محرك تعمية وحجب البيانات (PII & Sensitive Entity Masking)

- **FR-1.1** — فحص المدخلات فور وصولها للـ Gateway والتعرف آلياً على:
  - أرقام الهويات الوطنية والإقامات (10 أرقام).
  - أرقام السجلات التجارية (CR Numbers) والآيبان البنكي (IBAN).
  - أرقام الهواتف والبريد الإلكتروني والأسماء الشخصية.
- **FR-1.2** — استبدال البيانات بحقول مشفرة (مثل `<SAUDI_ID_1>` و`<CR_NUM_1>`)
  قبل إرسال أي استدعاء للـ LLM.
- **FR-1.3** — الحفاظ على جدول ربط عكسي (In-Memory Mapping Table) في ذاكرة
  الجلسة المشفرة فقط، لاستعادة البيانات الأصلية عند عرض المخرجات للمستخدم
  المصرح له.

### FR-2: استرجاع وتدقيق اللوائح الحكومية (Procurement RAG Engine)

- **FR-2.1** — ربط الوكيل بقاعدة بيانات متجهة تضم نصوص نظام المنافسات
  والمشتريات الحكومية، وضوابط المحتوى المحلي، ولوائح الشراء المباشر.
- **FR-2.2** — إلزام الوكيل بذكر السند النظامي ورقم المادة في كل تقرير تدقيق
  يصدره (Grounding & Citation).
- **FR-2.3** — منع الهلوسة عبر تقييد إجابات الوكيل بالسياق المسترجع فقط، ورفض
  الإجابة إذا غاب السند النظامي.

### FR-3: بوابة الأدوات والصلاحيات (Tool Execution Gateway & Guardrails)

- **FR-3.1** — توفير واجهات برمجية للأدوات الداخلية:
  - `check_vendor_eligibility(cr_number)` — فحص صلاحية السجل وشهادات السعودة والزكاة.
  - `verify_budget_ceiling(department_id, amount)` — التأكد من توفر ميزانية وعدم
    تجاوز السقف النظامي للشراء المباشر (مثل سقف 100 ألف ريال).
  - `create_procurement_order(vendor_id, amount, contract_terms)` — إنشاء مسودة أمر الشراء.
- **FR-3.2** — تطبيق الـ RBAC في طبقة الكود، ومنع الوكيل من استدعاء
  `create_procurement_order` إلا إذا كان التوكن المصاحب يحمل رتبة `Director`.

### FR-4: الاعتماد البشري الإلزامي (Human-in-the-Loop)

- **FR-4.1** — تعليق المعاملة ونقل حالتها إلى `PENDING_APPROVAL` إذا كان مبلغ
  الشراء يتجاوز السقف المحدد، أو إذا كانت نسبة المحتوى المحلي أقل من الحد المطلوب.
- **FR-4.2** — توفير مسار للـ Approver للاطلاع على تقرير الفحص والضغط على
  (اعتماد / رفض) مع تدوين الملاحظات.

### FR-5: سجل التدقيق والمطابقة (Audit Trail & Logging)

- **FR-5.1** — تسجيل حركة كاملة لكل معاملة بصيغة JSON غير قابلة للتعديل تشمل:
  - معرّف الموظف، الدور، الختم الزمني (UTC).
  - النص بعد التعمية (Masked Prompt).
  - الأدوات التي حاول الوكيل استدعاءها مع معاملاتها (Arguments).
  - حالة الاعتماد البشري والنتيجة النهائية.

## 4. المتطلبات غير الوظيفية (Non-Functional Requirements)

### NFR-1: الأمن وسيادة البيانات

- **NFR-1.1** — استضافة كافة الخدمات، قواعد البيانات، ومحرك الـ LLM داخل مراكز
  بيانات داخل المملكة (In-Kingdom Data Centers).
- **NFR-1.2** — تشفير البيانات أثناء النقل عبر بروتوكول TLS 1.3، وتشفير البيانات
  الساكنة باستخدام خوارزمية AES-256.
- **NFR-1.3** — استخدام سياسة عدم الاحتفاظ بالبيانات (Zero Data Retention) على
  مستوى خوادم استدلال النماذج.

### NFR-2: الأداء والاعتمادية

- **NFR-2.1** — زمن معالجة وإخفاء البيانات الحساسة (PII Masking) أقل من **150ms**
  للطلب الواحد.
- **NFR-2.2** — زمن الاستجابة الكلي لتوليد تقرير التدقيق المبدئي لا يتجاوز
  **5 ثوانٍ** باستخدام نماذج بحجم 7B إلى 14B بارامتر.
- **NFR-2.3** — جاهزية النظام (High Availability) بنسبة **99.5%** مع إمكانية
  التوسع الأفقي (Horizontal Scaling).

### NFR-3: النزاهة والموثوقية

- **NFR-3.1** — شفافية كاملة في مسار تفكير الوكيل (Chain-of-Thought Logging)
  لتمكين المراجعين من فهم أسباب التوصية بالقبول أو الرفض.

## 5. المعمارية الفنية المقترحة (Target Tech Stack)

| المكوّن | التقنية المقترحة | الدور الفني |
|---|---|---|
| Backend & API | Python / FastAPI | توفير البوابة وتدقيق الـ JWT Tokens والصلاحيات |
| Agent Framework | LangGraph | إدارة تدفق الحالة، الحلقات، واستدعاء الأدوات والـ Interrupts |
| PII Engine | Microsoft Presidio + Custom Regex | كشف وحجب الهويات والسجلات والبيانات المصنفة |
| Inference Engine | vLLM (Local / Sovereign Cloud) | تشغيل نموذج مثل Qwen2.5-7B/14B أو Llama-3.1-8B |
| Vector DB | ChromaDB أو PGvector | فهرسة لوائح نظام المنافسات والمشتريات الحكومية |
| Deployment | Docker & Kubernetes | نشر الخدمات داخل شبكة خاصة معزولة (Private VPC) |

## 6. سيناريو تجربة القبول والاعتماد (User Acceptance Scenario)

**المدخل** — موظف برتبة `Specialist` يدخل:

> «أرغب في ترسية شراء مباشر لكاميرات مراقبة على مؤسسة الأفق سجل تجاري
> 1010998877 بمبلغ 120,000 ريال وفق نظام المنافسات.»

1. **الاعتراض والحجب** — يحجب النظام رقم السجل التجاري ويستبدله بـ `<CR_NUM_1>`.
2. **التدقيق النظامي** — يسترجع الوكيل المادة المنظمة للشراء المباشر ويحدد أن
   السقف النظامي للشراء المباشر هو 100,000 ريال، وأن 120,000 ريال تتطلب منافسة
   عامة أو موافقة استثنائية.
3. **فحص الصلاحية** — يحاول الوكيل رفع أمر شراء، لكن بوابة الـ RBAC تمنع العملية
   لأن الموظف `Specialist` وليس `Director`، ولأن المبلغ يتجاوز السقف.
4. **المخرج النهائي** — يصدر الوكيل تقريراً نظامياً:

   > «تم رصد مخالفة للسقف المالي للشراء المباشر (المادة X). المعاملة تتطلب
   > موافقة صاحب الصلاحية وتعديل مسار الشراء لمنافسة محدودة.»

   مع توثيق الحادثة في سجل التدقيق.
